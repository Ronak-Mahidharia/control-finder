# Results: the vector database (step 5)

Generated by `scripts/run_database_check.py`. Earlier steps: [keyword search](results.md), [vector and hybrid search](results-vector-hybrid.md), [weighting and reranking](results-rerank.md).

## Setup
- **Database:** PostgreSQL 18.6 with pgvector 0.8.7, in Docker (`docker-compose.yml`, the image pinned by digest). The driver is pg8000, written in pure Python.
- **Table:** one row per active control (1,014), with its text and its embedding in a `vector(768)` column. The embeddings are the ones behind steps 3 and 4, committed in `embeddings/`. They're unit length, so the search uses the inner product, which is then the cosine similarity.
- **Searches:** exact, which orders by pgvector's `inner_product()` function, so every control is compared (no index can serve that order), with ties broken by catalog order like the in-memory search; and pgvector's HNSW index, through the `<#>` operator (m = 16, ef_construction = 64, its defaults). The index places each control at a random level, so it was built 10 times.
- **Loading:** 2.6 s for the 1,014 rows, one insert at a time in one transaction, and 0.18 s to build the index. The table and its indexes take 9.5 MB, 4.2 MB of it the HNSW index.

## Exact search gives the same results as the in-memory search
- **The same top 10** for 203 of 203 questions, and the same top 100 for 197. In the other 6, two neighbors swapped places, between ranks 36 and 95. Their similarities differ by at most 4.6e-07, which is float32 rounding.
- **Every published test score comes back:** vector search, both hybrid searches, and the reranker's 30 candidates per question, so the reranked scores too.

## The HNSW index
- **PostgreSQL decides when to use the index.** With the index in place and nothing forced, its planner used the index for a top 10 (Index Scan), so that result was approximate, and scanned the whole table for a top 100 (Seq Scan), which is exact. The numbers below force the index, and each setting's plan was checked; the exact search never used it, even forced.
- **pgvector's default returns only 40 rows.** It keeps ef_search candidates (40 by default) and returns no more than that, so a top-100 request silently gets 40.

## Reading these numbers
- **Exact top k found:** the share of the exact search's top k that the index also returned.
- **Hybrid top 10 changed:** questions whose fused top 10 differs from the one built from exact search.
- **Timings** depend on the computer and include the trip to the database and back, so CI doesn't check them. CI does check the exact search, the rows returned, and the planner's choices against a database of its own.
